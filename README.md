# 海外 AI 问题案例审核

这是一个面向海外游戏客服的质检、人工审核和知识沉淀工作台。它接收各渠道导出的 Excel，把每一行或已分段会话作为独立切片，交给 MaaS 工作流分析，并将可审核、可追溯的结果沉淀到本地数据库。

系统服务端口为 `8010`。局域网入口为 `http://10.3.200.61:8010`，本机也可使用 `http://127.0.0.1:8010`。

## 一次分析从哪里开始

管理员先在上传页创建批次并上传 Excel。上传、解析和分析是三个独立阶段：上传完成只表示文件已落盘；解析完成才会产生切片；只有用户显式点击“开始”后，待处理切片才会发送到 MaaS。这样可以先检查文件、映射和切片数量，再决定是否消耗模型调用。

一个 Excel 行或来源已给出的对话段对应一个 `QcSlice`。系统不会把它与其他行拼接，也不会基于完整会话重新切片。切片中保留原始渠道、游戏、地区、消息顺序、来源角色、时间和文本；MaaS 只能补充语言、翻译和分析结论，不能改写这些原始事实。

批次支持开始、暂停、恢复、终止和删除。暂停会停止领取新的待处理切片，已发出的请求仍会在返回后落库；终止后的批次不能再继续分析；删除会删除该批次的业务数据。分析结束后，队列会停在暂停态而不是擅自把业务批次标记为完成，便于人工确认结果后再进行下一步操作。

## Excel 解析和切片边界

解析器支持标准渠道（DC、VK、FB、LINE）、VIP、海外端内普客和 M 后台等导出格式。它先识别工作表和来源格式，再提取渠道、游戏、地区、会话标识、会话链接和原始消息；映射配置用于把来源字段转换为系统内统一的渠道、地区和游戏。

标准渠道文件若带有“客服”或“回复人”列，该列为空的行会被跳过，不创建切片也不会发送 MaaS。这避免把仅标成 `[客服]` 的群发或无实际客服处理的记录误当成人工会话。没有这两个表头的历史格式仍按对话内容解析。

消息角色由来源结构决定，而不是由模型从正文猜测：玩家为 `player`，AI 为 `ai`，真人客服为 `human_agent`，自动回复、系统身份、`*_push` 推送和 Discord 命令为 `system`，无法可靠识别的来源为 `unknown`。标准渠道和 VIP 会过滤空文本、未知角色、非自动回复的系统行，以及只剩玩家的无客服侧记录。活动群发、认证推送或仅使用“客服”前缀的广播不会作为人工客服内容进入分析。

海外端内的 `contentType=3` 会被保留为 `transfer_form_submitted` 转人工表单事实。该事实不是一段普通文案，而是后续转人工判断的重要证据。历史切片不会因代码更新被自动重写；需要用新规则验证的样本应重新上传并重跑。

## MaaS 调用和提示词

后端对每个切片只发起一次 OpenAI 兼容的 MaaS 对话请求。请求只有一条 User 消息：第一行是用于平台检索的 `slice_id=...`，空行后是切片 JSON。后端不发送 System Prompt、不携带 `chatId`，也不保存模型会话历史。

MaaS 工作流内分为两个职责节点：

- **AI对话质检**：翻译所有消息，只质检 `ai` 回复，并输出转人工结论。
- **知识库候选**：只从 `human_agent` 的实质性回答中判断是否能沉淀知识和术语，不输出转人工或 AI 质检结论。

当前有效的提示词副本分别在 [docs/maas-qc-system-prompt.md](docs/maas-qc-system-prompt.md) 和 [docs/maas-kb-system-prompt.md](docs/maas-kb-system-prompt.md)。修改文档本身不会改变 MaaS：必须把各文件从 `Role` 起的完整内容同步粘贴到对应工作流节点，之后重新分析批次，新的结果和统计才会生效。

[docs/maas-system-prompt.md](docs/maas-system-prompt.md) 是 1.0 单智能体存档，不应再配置到新工作流。`backend/services/analyzer.py` 中的 `QC_SYSTEM_PROMPT` 同样不是运行时提示词，不能把它当作现行规则修改。

## 质检和翻译逻辑

每条输入消息都要有对应的语言识别和中文翻译结果。后端以输入为准重建消息原文、角色、时间和顺序，因此模型即使回传了正文或角色，也不会覆盖原始记录。AI 质检仅针对 `speaker=ai`：没有 AI 消息时不应虚构质检问题。

模型最多输出三条有直接证据的问题，并且必须引用切片中真实存在、角色正确的消息 ID。后端会校验消息覆盖、翻译状态、置信度、问题数量、问题引用和排序；不符合协议的响应按失败处理，不会以脏数据进入结果列表或统计。

质检结论用于问题列表、报告、审核工作台和人工修订。模型原始结论与人工审核字段分开存储：审核人员补充的标签、评分、问题类型、处理去向和参考 Q/A 不会覆写 MaaS 原始结果，方便回看模型判断与人工判断的差异。

## 转人工口径和 TOP 统计

转人工分为三件彼此独立的事：是否出现人工消息、是否发生转接动作、转接或未转接是否合理。`human_agent` 只说明切片中出现了人工，不能单独证明已经转人工，也不能单独证明转人工合理。

`handoff_occurred=true` 仅表示可见的转接动作已经发生，例如明确的转人工话术、端内 `contentType=3` / `transfer_form_submitted` 表单，或系统/自动回复明确表示已登记、已受理、已排队并等待人工上线。仅有人工客服、玩家加人工、群发被标成人工，或只有“联系客服”“客服不在线”而没有转接、登记或排队证据，均不是已发生转人工。已登记、等人工上线属于已转人工。

“应转未转”只对应 `handoff_required`：当前确实需要升级人工、尚未发生转接，并且切片中没有人工客服。已有人工消息、已登记排队、纯人工会话都不能标为应转未转。附件或贴纸也不是天然转人工理由，只有玩家先发送附件/贴纸、之后出现转人工提示时，才可使用对应的转人工原因类型。

后端对模型输出再执行结构校验。无 AI 的切片若没有转接表单或可见的系统转接/登记过程，却被模型标成“已发生转人工”，会被拒绝；已有人工客服却被标成“应转未转”也会被拒绝。这样纯人工和无转接提示的切片不会污染统计。

管理页的“转人工类型 TOP”直接基于 `human_handoff` 聚合：已发生转人工只统计 `handoff_occurred=true`，应转未转只统计 `decision=handoff_required`。聚合不根据人工消息数量推断转人工，原因类型的桶、决策枚举和附件/贴纸绑定保持与 MaaS 协议一致。

## 知识候选和术语沉淀

知识库节点只评估人工客服回答。`answer_message_ids` 必须指向 `human_agent`；AI、玩家、系统、系统推送和广播都不能作为答案来源。没有人工客服消息时，结论只能是 `no_human_answer`。

可沉淀内容必须是可复用的规则、玩法、操作路径、道具奖励说明或低风险通用排查，而不是具体账号、订单、退款、封禁、补发、等待、受理或后台核查个案。需要玩家明确正向反馈的成熟内容才可直接进入已验证候选；低风险但尚无明确反馈的内容可以进入待验证候选；证据不足或事实风险不清时交给人工复核。活动规则不因缺少反馈自动进入待验证候选。

术语最多三条，只服务于已经成为知识候选的内容。知识候选、人工审核和知识池处理状态都保留独立的审计记录。审核人员可以维护 Q/A、知识库归属、分类和适用范围，再按“待录入、已整理、已导出、已上传”等状态推进，不会覆写 MaaS 原始建议。

## 审核、分配、报表和权限

问题和知识建议进入审核工作台后，管理员可以分配、改派、回收或取消任务；审核人员可以领取、开始、提交或退回。任务、编辑和状态变化都有日志，避免多人同时修改同一条记录而无法追溯。

报表页支持按批次、渠道、游戏、地区、问题类型、严重度等维度查看结果，生成 HTML 报告并导出 Excel。仪表盘展示整体结果和审核工作量。管理员页提供切片审计、转人工 TOP、映射配置、游戏 AI 配置、系统字典、MaaS 配置、备份和操作日志。

认证使用 JWT。普通用户只能进行授权范围内的审核；批次控制、模型配置、用户管理、数据映射、备份和全量审计属于管理员权限。数据库采用 SQLite WAL 和忙等待设置，分析请求等待 MaaS 时不会长期占用数据库会话，以降低写入和页面查询互相阻塞的风险。

## 运行和配置

推荐直接运行 [start.bat](start.bat)。脚本会先构建前端到 `backend/static`，再检查 8010 是否已监听；未启动时使用 Python 虚拟环境启动后端，并打开系统页面。前端单独开发可在 `frontend` 目录使用 Vite，发布前仍需构建静态产物。

MaaS 地址和密钥从 `backend/.env` 的 `MAAS_BASE_URL`、`MAAS_APP_KEY` 读取，超时由同文件的配置控制。可通过管理页更新配置；涉及后端 Python 逻辑、解析规则或配置加载方式的变更后，应重启 8010。仅修改 MaaS 提示词文档不需要重启后端，但必须同步粘贴到 MaaS 工作流节点。

后端测试位于 `backend/test_*.py`。与本次链路最相关的是 `test_standard_slice_filter.py`、`test_validate_slice_result.py`、`test_handoff_stats.py`、`test_overseas_transfer_form.py` 和 `test_knowledge_suggestion_display.py`；前端还提供批次门禁和转接表单展示的契约测试。测试应从 `backend` 目录使用项目约定的虚拟环境运行。
